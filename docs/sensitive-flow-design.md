# PowerShell7Guard 规则设计

本文说明规则的判定顺序及写入时机。第一版的实际覆盖范围和验证方法见文末。

Guard 要做两件事：**记住敏感数据去了哪里；判断待发送的数据是否敏感。** 读取、赋值和本地复制本身不拦截。只有能确认敏感数据将被发送、且规则要求阻断时，才拦截。

## 1. 规则从哪里读，状态往哪里写

| 存放位置 | 保存什么 | 谁来写 |
| --- | --- | --- |
| `config/sensitive.toml` 的 `[[rules]]` | 敏感文件、文件夹、文本及命中后的处理方式 | 用户配置规则 |
| 同一个 TOML 的 `[[rules.copy]]` | 已确认由该规则保护的数据生成的副本 | Guard 确认复制成功后写入 |
| 当前 Runspace 的内存状态表 | 临时变量的敏感标记和来源 | Guard 确认赋值后更新 |
| `state/persistent-variables.toml` | 永久变量的敏感标记和来源，不保存变量值 | Guard 确认持久化成功后写入 |

**配置字段：**

- `[[rules]]`：`id` 是规则编号，`files`、`folders`、`texts` 分别是文件、文件夹和敏感文本列表，`action` 指定命中后的处理方式。文件按实际路径匹配；文件夹包含子目录，按目录边界匹配；文本先做字面量匹配，不用正则。
- `[[rules.copy]]`：`path` 是副本路径，`copied_from` 是上一步来源，另存确认时间和事件编号。它写在所属规则下面；这就是需求里的「对应规则的 `.copy` 项」。`**` 不写进 TOML 表名。
- 永久变量表的键是**作用域、所属用户或机器、变量名**。表里记录规则编号和来源。`$global:` 不是永久变量，普通 `$env:` 赋值也只在当前进程生效。第一版仅在确认写入 User 或 Machine 环境变量后，才登记为永久变量。

## 2. 一条命令进入 Scan 后，按什么顺序处理

### 第一步：读出这条命令的输入和输出

- **AMSI** 提供待执行的脚本内容。
- **AST** 告诉规则引擎脚本里有哪些命令、参数、赋值、管道和重定向。
- **变量状态表** 提供变量已知的值或敏感来源。需要时只核对这条命令实际用到的变量，不重新扫描整个会话。
- **Runspace 和进程信息** 用来确定变量属于哪个会话、命令用的是哪个当前目录和用户。解析相对路径时，以 PowerShell 的文件系统位置为准，不能直接套用进程启动目录。

只看到文件名、变量名或命令名，不能判断数据真的被读取或发送。自定义函数、别名或动态参数改变了命令含义时，先确认实际执行目标。

### 第二步：从源头跟到目标

先从规则、已确认的副本和变量状态里找敏感来源。再按代码顺序判断，数据是否进入了变量、文件、管道或其他命令的输入。每一步保留**规则编号、来源和目标**，这样后来使用副本或变量时，仍能追到最初的敏感来源。

扫描时发现的操作先记为**准备执行**。简单赋值和管道能在执行前确定时，可以用于判定同一个脚本中的后续发送；如果中间有动态计算或未知命令，不能仅凭前后出现的名称就认定数据沿这条路线传递。

### 第三步：判定是否外发

1. 先识别命令是否准备上传，而不是下载、读取或做本地操作。
2. 确定它要发送的是什么：文件、请求正文、标准输入，还是 Git 对象。
3. 反向追踪这份输入：是否命中敏感规则，或来自已确认的敏感变量、副本。
4. 确认发送目标，按下表返回判定。

| 有什么证据 | 判定 |
| --- | --- |
| 发送内容、敏感来源和目标都确定，规则要求拦截 | **阻断**，日志写明来源、传播步骤和目标 |
| 看出可能外发，但关键输入、来源或目标拿不到 | **`Warning: Information missing`**，本规则不拦截 |
| 目标明确是本机回环（`127.0.0.0/8`、`::1` 或 `localhost`） | 默认检查；仅在显式设置 `trust_loopback = true` 时允许已确认的回环例外，日志记 `skip:loopback`。不要将同一局域网的其他主机当作回环。 |
| 要检查的输入都已核对，未命中规则 | **未命中**，本规则不拦截 |
| 当前不支持识别这类命令 | **未覆盖**，不记成「已检查、无敏感内容」 |

本地读取、赋值或复制只登记传播，不按外发阻断。仅发现网络连接，也不等于确认敏感内容已经发送。

## 3. 命令执行完以后，什么时候更新状态

- **临时变量**：管道结束后，只回读这次可能写入、且仍可见的变量。读到实际值再更新。遇到可能修改状态的命令，留着旧记录并标记待核对；下次只核对引用到的条目。
- **永久变量**：核对 User 或 Machine 的存储确实写入后，再写永久变量表。重启后如果只有旧标记、无法确认对应的值还是原来的值，就报告信息缺失，不靠旧标记拦截。
- **文件副本**：确认目标确实写入了敏感来源的数据后，才写入 `[[rules.copy]]`。直接复制可以在限额内比较源与目标内容；管道写入、追加或转换需要能说明来源和目标确实对应的证据。仅看到管道结束、目标文件已存在或时间戳变化，都不足以确认。
- **失败、阻断和覆盖**：被阻断的命令不登记结果。执行失败或结果读不到时，只记录待核对。副本或变量被改写、删除后，要核对旧记录，不能直接给新值沿用旧敏感标记。

Scan 先完成判定，再把日志和较慢的核对交给后台。后台拿到确认结果后更新状态，不反过来更改已返回的判定。多个 PowerShell 进程更新同一个 TOML 时，按顺序写入，每次先读取最新配置，只更新对应的 `copy` 项，不覆盖用户手写规则，也不创建备份。

## 4. 怎样增加对新命令的支持

每种命令由自己的**命令解析器**处理。解析器只需告诉规则引擎：**读了什么、写到哪里、有没有发送、发送的输入和目标是什么，以及执行后如何核实。** 新增工具不需要改敏感规则的格式。

| 命令 | 第一版要识别什么 |
| --- | --- |
| `Get-Content`、`Set-Content`、`Out-File`、`Copy-Item` | 识别来源、变量和文件目标。区分覆盖与追加；追加不会抹掉原先仍保留的敏感内容。 |
| PowerShell HTTP、`curl` | 识别正文、上传文件和标准输入。不能把响应输出文件或下载误当成上传。 |
| `scp` | 区分本地和远端，确认方向。目录和多个输入无法完全确定时，记信息缺失。 |
| `git push` | 检查候选本地引用的完整可达历史。不能只看工作区或最新提交：敏感文件在待推送历史里出现、后来删除，仍要检查。基线未知只警告。`git add` 和 `git commit` 不当作外发。 |

Scan 不启动外部程序、不等网络、不遍历大型 Git 历史。Git 可单独做预检；预检没准备好时，仍按「信息缺失只警告」执行。

## 5. 实现顺序与验收

1. **规则和状态**：能读 TOML，正确区分文件、目录、文本，能把副本归到正确规则。
2. **本地传播**：验证变量和副本只有在确认写入后才登记；失败、删除、覆盖不会留下错误的敏感标记。
3. **外发判断**：先接 PowerShell HTTP、`curl` 和 `scp`，核对上传、下载、管道和缺参四种情况。
4. **Git Push**：验证待推送历史、多个引用以及远端基线缺失。没有通过验收的命令不算已覆盖。

### 第一版的执行边界

- 确定的本地输入使用有大小上限的读取；物化字节预算由 `max_materialized_bytes` 配置。一般上传中未解析的递归目录、重解析点、非本地驱动器和未知编码不作确定判定。文本规则是区分大小写的字面量。
- 已验证 UTF-8、带 BOM 的 UTF-16/UTF-32、确定的 Base64 以及明确的 .NET 编解码调用。识别普通 ZIP/GZIP，默认检查最多两层嵌套、64 个 ZIP 条目和 256 KiB 展开数据。这些预算可通过策略配置，扫描时绝不落盘解压。损坏、格式未知或超限只警告，其他独立可证的命中仍有效。
- 已加载的 PowerShell 自带 `Compress-Archive` 支持有界的明确文件/目录。只有真实压缩成功并且 ZIP 成员及字节与计划对应，才登记源路径的敏感标记；通配符、第三方同名命令和不可确定输入只警告。
- 发送解析覆盖可确定的正文、文件或标准输入。动态控制流、未知参数和外部程序运行时才产生的内容不算已检查。
- AMSI 输入、脚本、执行路径上的语句和相关 AST 节点分别使用 `max_amsi_content_bytes`、`max_script_bytes`、`max_ast_statements` 和 `max_ast_nodes`。达到上限且未命中确定的阻断规则时，只警告；日志详细字段超出空间时，优先保留判定及其关键证据。
- 只判定 PowerShell 实际交给 AMSI 的 ScriptBlock；重复执行已编译的脚本块未必产生新的扫描。
- Git 由 `Prepare-GuardGitPush.ps1` 在 Scan 外准备，接受命名远端或显式网络 URL，以及受预算限制的分支或标签 refspec，也可仅给远端或省略远端与 refspec。支持分支简写、符号分支 HEAD、短目标、force、force-with-lease 和 set-upstream 选项。短目标与非分支引用冲突时要求完整 ref 名。默认推送支持单分支 simple、current、upstream 或明确配置的分支 refspec；Scan 核对 HEAD、配置及源引用。预检核对待推送历史中出现的文件，即使它们在最新提交中已删除。预检有效期由 `git_proof_lifetime_seconds` 配置，默认 60 秒。基线、引用、配置或对象无法核实时只警告。预检扫描本地候选历史，不从检查范围中扣除远端已经通告的对象。远端历史已有的匹配内容也可能触发规则。

### Git 预检自动化的接入点（未安装）

在受控的启动器中，先用本次推送的仓库、远端和 refspec 生成预检；预检缺失、失败、部分覆盖或命中阻断规则时，由启动器停止，而不是先发起 push 再查证。启动器随后必须复核 HEAD、配置和源引用，使用原始参数交给 Git。更准确的接入点是 Git 的 `pre-push` 钩子：从 Git 读取本次解析出的本地对象 ID 和远端对象 ID，核对实际候选对象；需要强制执行时配合受控入口或服务端规则。AMSI 的同步 Scan 不启动 Git、不连接远端。本次只改预检和校验证明，未安装钩子或自动推送任务。

Git 大 Blob 的文本规则直接读取 `git cat-file` 的对象流并复用本地文件的跨块匹配；不读取工作树同名文件。单 Blob 遵守 `max_file_bytes`、单 Git 子进程和预检时间预算。部分检查的明确文本命中仍保留，未读部分不算已检查。派生文件的大对象逐字节一致性验证仍是独立限制。

预检计数在 `[policy]` 可配置：`git_max_commits` 默认 128（最高 4096），`max_git_objects` 默认 2048（最高 32768），`git_max_path_bindings` 默认 4096（最高 65536）。时间、输出和单个内容的独立预算仍适用。
- 永久变量仅跟踪受支持的 User/Machine .NET 环境变量写入。使用持久状态前核对当前存储凭证；对于外部改写或凭证无法读取的情况，不沿用旧标签。状态文件不保存取到的环境变量值。
